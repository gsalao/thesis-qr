⏺ These are three separate questions — let me address each concretely.

  ---
  1. Where UAT fits in your thesis

  UAT belongs in your Evaluation / Results and Discussion chapter, not the
  technical design chapter. Its role in a cryptography-focused thesis is to
  argue practical deployability:

  - Your contribution is that threshold cryptography can be embedded in a real
  payment UX without degrading usability. Without UAT, a reviewer can dismiss
  the system as a crypto demo that nobody could actually use.
  - The two branches (main vs. small-qr) give you a comparative UX finding — you
   can cite which variant users found more intuitive and justify the design
  decision in the paper.
  - UAT also validates your functional requirements (users can initiate
  payments, nodes can approve, merchant can verify), which sets up your security
   testing as testing a working system rather than a toy.

  In the paper structure:
  Chapter N: System Evaluation
    N.1  Functional Testing (unit/integration — see §3 below)
    N.2  User Acceptance Testing (UAT results + branch comparison)
    N.3  Security & Performance Testing (penetration + latency)

  UAT is the bridge between "the cryptography is correct" and "this could
  replace existing PH fintech auth flows."

  ---
  2. Penetration testing — methodology

  Latency test (target: < 200 ms for QR verification)

  This is performance testing, not penetration testing in the strict sense, but
  it's standard to include both under a security evaluation umbrella.

  Instrument the code directly — add timing to the verify_payment handler:

  In server/controllers/socketHandler.js, find the verify_payment handler and
  wrap it:

  socket.on('verify_payment', async (data) => {
    const start = Date.now();
    // ... existing logic ...
    const elapsed = Date.now() - start;
    console.log(`[PERF] verify_payment: ${elapsed}ms`);
    socket.emit('payment_verified', { ...result, latencyMs: elapsed });
  });

  And on the client side in MerchantDashboard.jsx, measure round-trip:

  const t0 = Date.now();
  socket.emit('verify_payment', payload);
  socket.once('payment_verified', (result) => {
    console.log(`Round-trip: ${Date.now() - t0}ms`);
  });

  Run 30+ trials across small and large transactions, report mean ± std dev. BLS
   signature verification on BLS12-381 is fast (~5–15 ms on server), so your
  bottleneck will be network/socket overhead. Locally you'll be well under 200
  ms; on render.com, test against the deployed instance since that's the
  realistic scenario.

  ---
  MITM attack test (expected: tampered payload rejected)

  Important clarification for your paper: The QR payload is not encrypted — it's
   cryptographically authenticated. BLS signatures provide integrity, not
  confidentiality. An attacker who intercepts the QR can read the transaction
  data, but cannot forge or modify it without possessing threshold (3-of-5) key
  shares. This is the correct framing for your thesis.

  How to demonstrate it:

  Option A — Code-level tamper test (simplest, good for a thesis demo):

  Write a script that takes a valid completed transaction's QR payload, modifies
   the amount, and calls verify_payment:

  // server/test-mitm.js
  import { io } from 'socket.io-client';

  const socket = io('http://localhost:5001');

  // Use a real completed transaction's QR data
  const validPayload = { /* paste from a completed transaction */ };

  // Attacker modifies the amount
  const tamperedPayload = { ...validPayload, amount: 999999 };

  socket.emit('join_room', { nodeId: 99, role: 'merchant' });
  socket.on('room_joined', () => {
    socket.emit('verify_payment', { qrData: JSON.stringify(tamperedPayload) });
  });
  socket.on('payment_verified', (r) => console.log('Result:', r));
  socket.on('error', (e) => console.log('Rejected (expected):', e.message));

  Expected output: error event with signature invalid message.

  Option B — mitmproxy (more realistic, better for the paper):

  1. Install: pip install mitmproxy
  2. Run: mitmproxy --mode transparent -p 8080
  3. Configure your browser/Node to route through it
  4. Capture a verify_payment WebSocket frame
  5. Use mitmproxy's Python scripting to modify the payload in-flight
  6. Show the server rejects it

  For the thesis, Option A is sufficient to prove the claim. Option B is better
  if you want a network-layer demonstration. Screenshot/record both the tampered
   request and the rejection response.

  For transport-layer MITM (showing the socket traffic is protected): point to
  the fact that the production deployment (https://thesis-qr.onrender.com) uses
  TLS (WSS), so a network-level attacker sees only encrypted bytes. You can show
   this with Wireshark on the deployed instance.

  import { describe, it, expect } from 'vitest';
  import { hashMessage, signMessage, aggregateSignatures, verifySignature } from
   './cryptoUtils.js';
  import { PRIVATE_SHARES, JOINT_PUBLIC_KEY } from '../config/keys.js';

  const msg = 'test-transaction-123';

  describe('hashMessage', () => {
    it('produces consistent hash', () => {
      expect(hashMessage(msg)).toEqual(hashMessage(msg));
    });
    it('different inputs produce different hashes', () => {
      expect(hashMessage('a')).not.toEqual(hashMessage('b'));
    });
  });

  describe('threshold signature', () => {
    it('1-of-5: single share verifies (low-value tx)', () => {
      const sig = signMessage(PRIVATE_SHARES[0], msg);
      // aggregate with just one share (nodeId=1)
      const agg = aggregateSignatures([{ nodeId: 1, sig }], msg);
      expect(verifySignature(agg, JOINT_PUBLIC_KEY, msg)).toBe(true);
    });

    it('3-of-5: three shares verify (high-value tx)', () => {
      const shares = [1, 2, 3].map(i => ({
        nodeId: i,
        sig: signMessage(PRIVATE_SHARES[i - 1], msg)
      }));
      const agg = aggregateSignatures(shares, msg);
      expect(verifySignature(agg, JOINT_PUBLIC_KEY, msg)).toBe(true);
    });

    it('tampered message fails verification', () => {
      const shares = [1, 2, 3].map(i => ({
        nodeId: i,
        sig: signMessage(PRIVATE_SHARES[i - 1], msg)
      }));
      const agg = aggregateSignatures(shares, msg);
      expect(verifySignature(agg, JOINT_PUBLIC_KEY,
  'tampered-message')).toBe(false);
    });

    it('2-of-5 is insufficient for high-value threshold', () => {
      const shares = [1, 2].map(i => ({
        nodeId: i,
        sig: signMessage(PRIVATE_SHARES[i - 1], msg)
      }));
      const agg = aggregateSignatures(shares, msg);
      expect(verifySignature(agg, JOINT_PUBLIC_KEY, msg)).toBe(false);
    });
  });

  Run with:
  cd server && npm test

  The tamper test and the insufficient-shares test directly support your thesis
  claims in the paper. Screenshot passing tests for your appendix.
